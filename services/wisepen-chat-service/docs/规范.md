---

## 一、`__init__.py` 导出规范

- 所有 `__init__.py` 文件**必须**使用 `__all__` 显式声明导出内容，只列出对外暴露的公共接口。
- **禁止**在非 `__init__.py` 文件中定义 `__all__`。

---

## 二、类型注解规范（基于 `typing` 模块）

**允许使用：**
- `Optional[X]`：表示可为 None 的类型，**禁止**写成 `X | None` 或 `str | None`
- `Union[X, Y]`：表示多类型联合，**禁止**使用 `X | Y` 的写法
- `List[X]`、`Tuple[X, ...]`、`Dict[K, V]`、`Set[X]`：**禁止**用内置小写 `list[X]`、`tuple[X]`、`dict[K, V]` 替代

**禁止使用：**
- `|` 联合类型语法（如 `str | None`、`int | str`）
- 内置泛型小写形式（如 `list[str]`、`dict[str, int]`）
- 独立的 `Any` 注解（Python 是动态类型语言，不应滥用 `Any`）
- 复杂的自定义泛型 `TypeVar`，除非有明确必要

---

## 三、命名与访问控制规范

- 所有**模块内部**使用的变量、函数、类，必须以**单下划线前缀**命名（如 `_helper()`、`_INTERNAL_CONFIG`）。
- 无下划线前缀的命名视为**公共接口**，需保持克制，只暴露真正对外的部分。

---

## 四、异常类规范

- **禁止**定义仅有 `pass` 的自定义异常类：
```python
  # ❌ 禁止
  class MyError(Exception):
      pass
```
- 自定义异常必须有实际意义：携带结构化字段、自定义 `__init__`、或有明确文档字符串说明其语义。
- 若只需要一个具名异常且无额外信息，优先复用标准库异常（`ValueError`、`RuntimeError`、`KeyError` 等）。

---

## 五、错误处理规范

- **禁止静默吞异常**，以下写法一律不允许：
```python
  # ❌ 禁止
  try:
      val = int(user_input)
  except Exception:
      pass

  # ❌ 禁止 —— 无声替换，调用方无感知
  try:
      val = int(user_input)
  except ValueError:
      val = 0
```
- 类型转换、IO 操作、外部调用等，**必须**让异常向上传播，或显式记录后重新抛出。
- **例外**：安全相关场景（如密码比对、token 校验）允许静默处理，但**必须**用注释说明原因。
- 资源清理场景（如 `close()`、`stop()`）允许吞异常以确保后续资源释放，但**必须**加 `log_fail` 记录，不得裸 `pass`。
- `except:` 裸捕获一律改为 `except Exception:`。

---

## 六、防御性编程规范

- **禁止**对语义上不可能出现的输入做防御：
```python
  # ❌ 禁止 —— timeout 语义上就是正数
  if timeout < 0:
      raise ValueError("timeout must be positive")

  # ❌ 禁止 —— 内部函数，调用方可控
  if items is None:
      items = []

  # ❌ 禁止 —— 类型系统已保证，or None 无意义
  value = value or None
```
- 防御性检查**只在以下场景允许**：
  1. 公共库 / SDK 的对外入口，调用方不可控
  2. 跨进程、跨网络的数据边界（如反序列化、HTTP 入参）
  3. 有明确历史 bug 记录的回归点（用 `assert` + 注释说明）
- 评估后决定保留的防御，必须在代码中注释说明保留原因，否则下次 review 视为违规。

## 七、注释与日志语言规范

**使用中文的场景：**
- 所有 `logging` 日志信息
- 所有 `docstring`（模块、类、函数的文档字符串）
- 所有行内注释（`#` 注释）

**使用英文的场景：**
- 会**透传给模型**的报错信息（如 Tool Error、工具调用失败的 error message）
- **发送给模型**的 prompt 片段、系统消息、指令模板中的固定文本
- 模型 API 交互层的结构化字段值

**判断标准：**
> 这段文字，最终的读者是**人**还是**模型**？人读 → 中文，模型读 → 英文。

---

## 八、日志函数使用规范

**`log_fail` —— 仅用于真实失败场景：**
- 调用外部服务失败
- 资源清理失败（page 关闭、连接断开等）
- 预期应成功但实际出错的情况

**`log_event` —— 用于策略决策、过程观测、质量警告等非失败场景：**
- 质量阈值未达标（如相似度低、置信度不足）
- 主动跳过、降级、截断等策略行为
- 流程中的关键节点观测

**判断标准：**
> 问自己：**"这件事本来应该成功吗？"**
> 应该成功但没成功 → `log_fail`；系统按预期策略运行，结果不理想 → `log_event`。

## 九、代码格式规范

- **禁止**将语义更清晰的多行参数写法强行压缩为单行：
```python
  # ❌ 禁止 —— 强行单行，参数语义不清晰
  result = do_something(user_id, session_id, max_retry=3, timeout=30, fallback=True)

  # ✅ 正确 —— 多行写法，参数意图一目了然
  result = do_something(
      user_id,
      session_id,
      max_retry=3,
      timeout=30,
      fallback=True,
  )
```
- 判断标准：**参数超过 2 个，或存在关键字参数时，优先使用多行写法**。
- 单行写法只适用于参数极少且语义自明的场景：
```python
  # ✅ 可接受 —— 参数少且语义自明
  open(filepath, "r")
  max(a, b)
```
- 多行写法的最后一个参数**必须带尾随逗号**，便于 diff 追踪和后续添加参数。
