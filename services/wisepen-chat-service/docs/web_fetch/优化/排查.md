请对当前项目代码做一次“简洁性与可维护性专项排查”。

背景：
当前功能已经基本稳定，接下来重点不是继续加功能，而是检查代码是否开始膨胀、过度抽象、重复造轮子，确保后续维护成本可控。

总体目标：
1. 找出超过 30 行的函数，判断是否存在膨胀、职责混杂、难以 review 的问题。
2. 找出各种辅助函数，判断是否存在：
   - 只使用一次但被过度抽象；
   - 一行包装函数；
   - 重复造轮子；
   - 名字很大但逻辑很小；
   - 实际只是隐藏业务逻辑；
   - 和已有工具函数功能重复。
3. 不要盲目重构。
4. 不要为了“解耦”而制造更多文件和跳转。
5. 输出排查报告和具体修改建议，不要直接大规模改代码。

核心原则：

一、超过 30 行的函数重点检查

请扫描所有函数 / 方法，找出逻辑行数超过 30 行的函数。

对每个超过 30 行的函数，判断它属于哪种情况：

1. 合理较长：
   - 主流程清晰；
   - 分支是业务自然分支；
   - 局部逻辑内联更容易读；
   - 抽出去反而增加跳转成本。

2. 需要拆分：
   - 同时做参数解析、业务处理、日志、格式化、异常处理；
   - 嵌套层级过深；
   - 存在多段互不相关的逻辑；
   - 同类代码重复多次；
   - try/except 包裹范围过大；
   - 函数名无法准确覆盖实际职责。

3. 应该回收抽象：
   - 函数长是因为调用了太多小 helper，主流程反而不直观；
   - helper 只用一次，且只是简单包装；
   - 代码被拆碎后 review 成本更高。

输出格式：

函数：
- 文件：
- 函数名：
- 当前行数：
- 判断：合理 / 建议拆分 / 建议回收抽象
- 原因：
- 建议：

二、重点检查辅助函数

请重点扫描以下类型的函数：

- utils 下的函数；
- 模块级 helper；
- 类中不使用 self 的方法；
- log_xxx helper；
- parse_xxx / normalize_xxx / format_xxx / build_xxx / create_xxx / validate_xxx 函数；
- 只在一个地方调用的函数；
- 名字像通用工具但实际只服务当前模块的函数。

判断标准：

1. 应该保留的 helper：
   - 被多处调用；
   - 有明确业务语义；
   - 封装一段完整逻辑，而不是一行包装；
   - 减少重复；
   - 统一重要协议或格式；
   - 隔离第三方库边界；
   - 隔离复杂错误处理；
   - 逻辑本身值得单独测试。

2. 应该内联的 helper：
   - 只调用一次；
   - 只有一两行；
   - 只是换了个名字包装已有函数；
   - 抽出来后调用者更难读；
   - 没有独立测试价值；
   - 没有复用价值；
   - 只是为了“看起来解耦”。

3. 应该移动位置的 helper：
   - 当前在 utils，但只服务单个模块；
   - 当前在类里，但不使用 self；
   - 当前在业务模块里，但多个模块重复实现了类似逻辑；
   - 当前是全局 helper，但应该属于某个具体领域模块。

三、检查重复造轮子

请检查项目中是否存在功能相似但重复实现的函数，例如：

- URL 判断：
  - is_valid_http_url
  - is_document_url
  - document extension 判断

- 文本处理：
  - normalize_text
  - normalize_markdown
  - strip / 空行压缩逻辑

- 参数解析：
  - parse_int
  - int(...) 包装
  - limit / offset 默认值处理

- 日志：
  - log_xxx_success
  - log_xxx_fail
  - 多处重复 log_fail("同一阶段", ...)

- 分块 / 截断：
  - content[:N]
  - TOOL_RESULT_MAX_CHARS 手写截断
  - ToolContentStore 分块协议之外的局部截断

- 缓存：
  - 手写 TTL / LRU
  - TTLCache
  - OrderedDict 模拟缓存

- 文档类型判断：
  - magic bytes 检测
  - MIME 判断
  - 扩展名兜底

- HTML / 页面判断：
  - looks_like_html
  - anti-crawl / block page 检测
  - 空壳页面判断

- 建议保留哪个实现：
- 是否需要移动到 utils / 当前模块 / application 层：
- 是否存在行为差异：
- 风险：

四、检查过度抽象

请特别找出以下问题：

1. 单次使用 helper：
   例如：
   - build_xxx 只调用一次；
   - log_xxx 只调用一次；
   - decode_xxx 只调用一次；
   - get_xxx 只有一行。

2. 概念型 helper：
   函数名字看起来很高级，但只是把一段很短的代码换个名字。

3. 伪解耦：
   把逻辑拆到 utils 后，调用方和实现方都更难理解。

4. 函数容器类：
   类中大量方法不使用 self。
   这类方法应该变成模块级函数，或者直接内联。

5. 过度 DI：
   纯函数、无状态 helper 不应该注册到 container。
   只有涉及生命周期、配置、外部 client、复杂装配、测试替换的对象才应该进入 container。

五、检查膨胀的内联函数

不是所有长函数都应该拆，也不是所有内联都合理。

请检查是否有函数中存在“大段内联逻辑”，例如：

- 一个函数里同时包含多个阶段：
  - 参数校验
  - 外部请求
  - 内容处理
  - 结果格式化
  - 缓存读写
  - 日志汇总

- 一个函数里出现多个重复结构：
  - 多个 if 分支做相似日志；
  - 多个 except 分支只差日志文案；
  - 多个工具返回格式拼接；
  - 多个缓存 miss / hit 处理。

判断是否应该提取时使用以下规则：

应该提取：
- 同类逻辑重复 2 次以上；
- 提取后能显著缩短主流程；
- 提取后函数名能准确表达业务动作；
- 提取出的逻辑有独立测试价值；
- 提取出的逻辑会被多个调用方复用。

不应该提取：
- 只出现一次；
- 只有一两行；
- 提取后只是增加跳转；
- 函数名只是重复代码内容；
- 提取后反而隐藏关键业务分支。

六、检查日志简洁性

重点检查：

1. 初始化日志是否重复：
   - Docling 初始化；
   - SteelFetcher 初始化；
   - LocalScriptFetcher 初始化；
   - container 装配相关日志。

重复初始化日志通常说明生命周期管理有问题，应优先检查 DI / Singleton，而不是简单删除日志。

2. 运行日志是否保留：
   以下日志不要误删：
   - 单个 URL 抓取失败；
   - HTTP 状态错误；
   - 内容为空；
   - 内容过短；
   - 内容处理失败；
   - 所有抓取器均失败；
   - 子进程超时；
   - 文档解析失败。

3. 日志 helper 是否必要：
   - 多处重复且字段一致，可以保留；
   - 单处使用，不要抽 helper；
   - helper 不应隐藏关键字段。

七、检查长内容协议一致性

请重点检查是否还存在绕过 ToolContentStore 的局部截断：

- content[:3000]
- result[:limit]
- markdown[:N]
- text[:N]
- TRUNCATION_MARKER 直接拼接
- TOOL_RESULT_MAX_CHARS 手写截断

判断：
1. 如果这是工具最终返回窗口控制，可以保留。
2. 如果这是某个工具内部抓取到长正文后的局部截断，应该改为 ToolContentStore / format_windowed_content / tool_content_read 协议。
3. 不要让模型误以为它读到了全文。
4. 能缓存完整内容的地方，应返回 ToolContent Metadata。
5. content_cached=false 时不能提供 next_offset。

八、检查 container 注册边界

请检查 container.py：

1. 是否注册了过多无状态 helper。
2. 是否还有工具类内部 Optional 依赖兜底创建复杂对象。
3. 是否有 provider 顺序问题。
4. 是否有 provider 分组不清晰。
5. 是否有本该由 container 装配的对象仍在业务类里 new。
6. 是否有不该进 container 的纯函数进了 container。

判断标准：
- 纯函数、无状态 helper：直接 import。
- 有状态但无复杂装配，且语义上是共享内存状态：可以模块级实例。
- 有状态且涉及配置、外部 client、复杂依赖、共享生命周期：进 container。
- Tool / Coordinator / Repository / Provider / Client：原则上由 container 创建。
