同意，这样更干净。

`parse_int` 这种函数只是**局部参数解析辅助**，不是业务处理，也没有明显复用价值。强行放进 `utils/text_utils.py` 反而会让 utils 变成杂物间。

建议最终结构收敛成：

```text
chat/application/web_fetch/
    content_processor.py
    fetch_coordinator.py
    document_parser.py

    utils/
        __init__.py
        url.py
        page.py
```

## 职责划分

### `utils/url.py`

只放 URL / 链接类型判断：

```python
from urllib.parse import urlparse


__all__ = [
    "DOCUMENT_EXTENSIONS",
    "is_valid_http_url",
    "is_document_url",
]


DOCUMENT_EXTENSIONS = (
    ".pdf",
    ".doc",
    ".docx",
    ".xls",
    ".xlsx",
    ".ppt",
    ".pptx",
)


def is_valid_http_url(url: str) -> bool:
    parsed = urlparse(url)
    return parsed.scheme in {"http", "https"} and bool(parsed.netloc)


def is_document_url(url: str) -> bool:
    path = urlparse(url).path.lower()
    return path.endswith(DOCUMENT_EXTENSIONS)
```

使用处：

```python
from chat.application.web_fetch.utils.url import is_valid_http_url
from chat.application.web_fetch.utils.url import is_document_url
```

---

### `utils/page.py`

只放页面内容判断 / 页面状态类检测：

```text
PageBlockDetection
detect_page_block
should_degrade_page
looks_like_anti_crawl
```

也就是反爬、登录、验证码、JS 空壳判断都放这里。

`ContentProcessor` 使用：

```python
from chat.application.web_fetch.utils.page import detect_page_block, should_degrade_page
```

## 不建 `text_utils.py`

暂时不建：

```text
utils/text.py
```

```text

normalize_text 当前只在 ContentProcessor 或 DocumentParser 内局部使用，先保留在对应模块。
```

如果未来多个文件都需要同一个 `normalize_text`，再抽：

```text
utils/text.py
```

现在不用提前抽象。

## `parse_int` 保留在原模块

例如 `WebFetchTool`：

```python
def parse_int(value: Any, default: int) -> int:
    try:
        return int(value)
    except (TypeError, ValueError):
        return default
```

`ToolContentReadTool` 里如果也需要，可以各自保留一份。
这点重复可以接受，因为它不是业务逻辑，强行共享反而增加跳转成本。
