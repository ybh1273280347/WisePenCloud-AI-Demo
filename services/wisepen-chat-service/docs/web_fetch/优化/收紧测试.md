是，这就是典型的工程复杂度雪球。最开始只是：

```text
httpx 抓一下
不行就 Steel 浏览器抓一下
返回 Markdown
```

然后真实世界开始报复：

```text
页面反爬
JS 空壳
PDF 粘连
文档解析质量
长内容截断
工具续读
Docling OCR 爆内存
PaddleOCR 显式链路
worker 生命周期
URL SSRF
redirect 绕过
container 膨胀
settings 膨胀
```

这不是你一开始设计错了，而是 **“服务端替用户访问任意 URL + 给模型消费结果”** 这个能力天然就会长出这些边界。

但现在确实要收手，不能再无限扩。

## 现在应该重新定边界

我建议把 web fetch 重新收敛成三层：

```text
第一层：普通网页抓取
    httpx static
    steel browser fallback
    trafilatura clean
    ToolContentStore

第二层：文档解析
    Docling OCR=False
    native fallback
    只处理 PDF/DOCX/PPTX/XLSX

第三层：显式 OCR
    只有 force_ocr=true
    PaddleOCR worker
    只作为 supplement
```

然后明确一条红线：

```text
任何新复杂度，除非修安全问题或稳定性问题，否则不再进入 web_fetch 主链路。
```

## 当前最小必要完成线

我觉得现在只剩这几件必须做：

1. **StaticFetcher redirect SSRF 修掉**
   这是安全问题，必须修。

2. **安全失败终止降级链**
   否则 StaticFetcher 拒绝了，Steel 又绕过去，安全修复等于没修。

3. **OCR worker 接入 shutdown close**
   这是资源生命周期问题，应该收尾。

4. **settings / container 只做分组整理，不再扩功能**
   这是维护性收口。

除此之外，先别加：

```text
不要加 ocr_pages
不要加更多 OCR backend
不要加 PaddleOCR-VL
不要加 PP-Structure
不要做自动 OCR fallback
不要做复杂 DNS transport
不要做独立 OCR 服务
不要做全套浏览器 redirect 安全沙箱
```

## 一个现实判断

你现在已经从“抓页面”走到了“内容获取子系统”。

它本质上不是一个小工具了，而是：

```text
Content Acquisition Pipeline
```

里面有：

```text
fetch
browser fallback
parse
clean
cache
window read
document extraction
OCR supplement
security policy
```

所以难受是正常的。关键是别继续让它变成“万能内容处理平台”。

## 建议写进项目原则

```text
web_fetch 的目标不是完美理解互联网内容；
web_fetch 的目标是稳定、安全地获取可供模型阅读的文本。

默认链路必须轻：
    static fetch
    browser fallback
    content clean
    document parse
    ToolContentStore

高成本能力必须显式：
    OCR
    browser
    long-document reading

安全问题优先于可用性：
    SSRF 拒绝后不得降级绕过

不做自动魔法：
    不自动 OCR
    不自动多 backend 尝试
    不自动绕过安全限制
```

## 现在的执行建议

最后收口提示词可以这样写：

```text
请停止扩展 web_fetch 新能力，只做收口修复。

当前目标不是继续增强抓取能力，而是把已有能力稳定下来。

只允许处理以下事项：
1. StaticFetcher redirect SSRF 修复。
2. UrlSecurityError / Unsafe URL 失败必须终止 FetchCoordinator 降级链。
3. LocalOcrProcessor.close() 接入应用 shutdown。
4. container / settings 做分组整理，保持外部访问路径不变。
5. 补最小必要测试或手动验证。

禁止：
1. 不新增 OCR 参数。
2. 不新增 OCR backend。
3. 不新增 ocr_extract tool。
4. 不新增复杂 DNS transport。
5. 不新增自动 OCR fallback。
6. 不新增文档解析 backend。
7. 不拆成独立服务。
8. 不改变 ToolContentStore 协议。
9. 不改变 web_fetch 默认行为。

web_fetch 的稳定边界：
- 默认只抓取和解析文本。
- OCR 只在 force_ocr=true 时作为 supplement。
- 安全拒绝必须终止链路。
- 长内容必须走 ToolContentStore。
```

你现在的直觉是对的：
**不能再因为每发现一个边界就继续扩一层架构。**

修完安全收口点之后，应该冻结 web_fetch 一段时间，只做测试和观察。
