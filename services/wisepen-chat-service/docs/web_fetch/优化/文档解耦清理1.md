好，**命名已经结束**，下一轮就不要再纠结文件名了。现在进入“可读性 / 可维护性 review”的实质阶段。

我建议接下来按这个顺序处理它提到的修改：

## 总顺序

```text
1. public API / __init__.py / __all__
2. 无意义防御性编程
3. errors.py / 错误码体系
4. metadata / warnings 语义
5. worker.py 内部 helper
6. 测试与审计脚本
```

这个顺序的原因是：先确定**对外边界**，再清理**调用方式**，最后才处理局部实现细节。PEP 8 明确建议用 `__all__` 声明 public API，同时内部接口仍使用单下划线，且外部模块不应依赖间接导入的实现细节；这个正好符合你现在的风格方向。([Python Enhancement Proposals (PEPs)][1])

# 1. 先处理 `__init__.py` / `__all__`

## 处理意见

**保留 `__init__.py` 里的 `__all__`。**

但要满足三条：

```text
1. 只导出 public API。
2. 不导出内部 helper。
3. 不做旧路径兼容 re-export。
```

## 应该怎么改

每个子包的 `__init__.py` 只导出它真正的公共入口。

例如 `pdf/__init__.py`：

```python
from .parser import PdfParser
from .page_classifier import PageClassifier
from .text_extractor import TextExtractor
from .page_renderer import PageRenderer
from .table_extractor import TableExtractor
from .scanned_table_extractor import ScannedTableExtractor

__all__ = [
    "PdfParser",
    "PageClassifier",
    "TextExtractor",
    "PageRenderer",
    "TableExtractor",
    "ScannedTableExtractor",
]
```

不要这样：

```python
from .parser import _count_page_types
from .parser import _format_warning
```

也不要这样：

```python
from .primary_parser import OfficePrimaryParser as DoclingOfficeParser
```

## 验收

```bash
rg "__all__" src/chat/application/document_parse
```

期望：只出现在 `__init__.py` 或明确公共聚合模块里。

# 2. 再删无意义防御性编程

这是你现在最重要的风格点。

## 处理意见

凡是 OpenAI tool schema 已经约束类型的参数，业务层不要做宽容转换。

## 应该删除的模式

```python
file_ref = str(kwargs.get("file_ref", "")).strip()
force_ocr = bool(kwargs.get("force_ocr", False))
offset = int(kwargs.get("offset", 0))
```

## 改成

```python
file_ref = kwargs["file_ref"]
force_ocr = kwargs.get("force_ocr", False)
offset = kwargs.get("offset", 0)
```

注意：**不宽容错误类型**。如果协议层失守，就让它失败，不要业务层猜测模型意图。

## 只保留必要校验

保留这些：

```text
- 后缀是否支持
- file_ref 是否 resolve 成功
- local_path 是否存在
- 文件大小 / 页面像素 / 资源上限
- 第三方库返回空结果
- 第三方库异常包装
- URL 安全边界
```

删除这些：

```text
- str(...) 宽容转换
- bool(...) 宽容转换
- int(...) 宽容转换
- 旧字段名兼容
- 空字符串兜底
- 多类型兼容输入
```

社区实践上，Schema / 边界层负责输入契约，业务层负责业务约束；混在一起会让错误被静默“修正”，反而降低可维护性。PEP 8 的 public/internal interface 规则也强调边界清晰，而不是让内部实现去补救错误调用。([Python Enhancement Proposals (PEPs)][1])

## 验收

```bash
rg "str\\(kwargs|get\\(\" src/chat/application/document_parse
rg "bool\\(|int\\(" src/chat/application/document_parse
```

这些命中不一定全错，但需要逐个确认是不是“宽容模型参数”。

# 3. 然后处理 `errors.py` / 错误码体系

## 处理意见

**删除错误码体系。**

如果 `errors.py` 只是这些：

```text
DocumentParseError
UnsupportedDocumentTypeError
EmptyDocumentParseResult
ParserDependencyError
error_code
internal_code
status_code
```

就删。

## 替代规则

```text
ValueError:
- 不支持的后缀
- 解析结果为空
- 业务参数不合法

RuntimeError:
- 第三方后端不可用
- 后端失败且无法降级

warnings:
- 单页失败
- 表格失败
- OCR 失败
- fallback 发生
```

## 示例

```python
raise ValueError("不支持的文档类型：.html。HTML 应由 web_fetch 处理。")
```

```python
warnings.append(
    f"table_parse_failed: page={page_number}: {type(exc).__name__}: {exc}"
)
```

不要：

```python
raise UnsupportedDocumentTypeError(code="DOCUMENT_PARSE_001")
```

## 验收

```bash
rg "DocumentParseError|UnsupportedDocumentTypeError|EmptyDocumentParseResult|ParserDependencyError|error_code|internal_code|status_code" src tests
```

期望无生产代码结果。

# 4. 再统一 metadata / warnings

这一步不是为了“更复杂”，而是为了后续排查问题不用猜。

## PDF metadata

```python
{
    "parser": "PdfParser",
    "pdf_backend": "pymupdf",
    "ocr_backend": "paddleocr",
    "table_backends": ["camelot", "pp_structure"],
    "page_type_counts": {
        "text": 0,
        "mixed": 0,
        "scanned": 0,
        "empty": 0,
    },
}
```

## Office metadata

```python
{
    "parser": "OfficeParser",
    "selected_parser": "docling|markitdown|python_fallback",
    "fallback_chain": ["docling", "markitdown", "python_fallback"],
}
```

## Spreadsheet metadata

```python
{
    "parser": "SpreadsheetParser",
    "spreadsheet_backend": "pandas",
    "sheet_count": 3,
}
```

## warnings 格式

```text
page_parse_failed: page=3: ValueError: ...
table_parse_failed: page=2: RuntimeError: ...
ocr_failed: page=5: TimeoutError: ...
docling_failed: RuntimeError: ...
markitdown_failed: ValueError: ...
python_fallback_used: reason=markitdown_failed
```

重点：

```text
PP-Structure 失败必须是 table_parse_failed。
PP-Structure 失败不能丢 OCR 文本。
Docling 失败必须是 docling_failed。
MarkItDown 失败必须是 markitdown_failed。
```

# 5. 最后处理 `worker.py`

## 处理意见

`worker.py` 的小 helper 最后处理，不要第一刀就动。

## `get_bool`

如果它只是为了宽容这些：

```text
"true"
"false"
1
0
None
```

那删掉，直接读 bool 字段。

```python
use_doc_orientation_classify = request.get("use_doc_orientation_classify", False)
use_doc_unwarping = request.get("use_doc_unwarping", False)
use_textline_orientation = request.get("use_textline_orientation", False)
```

## 不能改

```text
- worker JSON 协议
- stdout / stderr 行为
- response 字段
- lazy import PaddleOCR
- collect_texts 的核心逻辑
```

`collect_texts` 如果是在处理 PaddleOCR 复杂返回结构，可以保留。不要为了“小函数洁癖”强拆。Google Python Style Guide 强调一致性和可读性，但不是机械把所有长函数切碎。([Python Enhancement Proposals (PEPs)][1])
