本次清理只做三类事情：
1. 开发者日志与内部异常信息中文化；
2. 精简冗余代码，重点审查超过 30 行的函数；
3. 统一为项目当前约定的代码风格。

============================================================
一、日志与内部错误信息中文化
============================================================

目标：
只中文化“开发者排查用”的日志和内部异常信息，方便开发者定位问题。

需要处理：

1. log_ 系列函数调用：
   - log_ok(...)
   - log_fail(...)
   - log_error(...)
   - log_event(...)
   - 其他以 log_ 开头的项目日志函数

2. 内部异常信息：
   - RuntimeError(...)
   - ValueError(...)
   - OcrProcessingError(...)
   - OcrWorkerError(...)
   - UrlSecurityError(...)
   - 其他自定义 xxxError(...) 中用于开发者排查的 message

要求：

1. 将日志 stage / message 改成中文。
2. 将内部异常信息改成中文。
3. 保留必要技术名词：
   - URL
   - HTTP
   - OCR
   - PDF
   - JSON
   - stdout
   - stderr
   - ToolContent
   - PaddleOCR
   - Docling
   - PyMuPDF
   - Steel
   - SSRF
   - fetcher
   - worker
4. 不翻译协议字段、变量名、配置名、工具名。
5. 不改变异常类型。
6. 不改变错误分支行为。
7. 不吞异常。
8. 不把原本应该 raise 的地方改成 return。
9. 不把原本应该返回 Tool Error 的地方改成异常。

重要边界：

不要翻译返回给模型上下文的内容，包括但不限于：

1. Tool Result：
   - "[Tool Result] ..."
   - "[Tool Error] ..."
   - "[ToolContent Metadata]"
   - 工具返回给模型阅读的正文

2. 工具 schema / description：
   - tool name
   - tool description
   - parameters_schema 中的 description
   - ToolContent Metadata 字段名

3. 模型可见内容：
   - OCR Supplement
   - Document Parse Result
   - Source / Backend / Page 等 Markdown 标题
   - web_fetch 返回内容
   - tool_content_read 返回内容
   - cache_and_window / format_windowed_content 输出

4. worker JSON 协议字段：
   - ok
   - error
   - message
   - backend
   - text
   - line_count
   - shutdown

5. 对外 API / 协议约定：
   - content_id
   - next_offset
   - truncated
   - content_cached
   - content_type
   - metadata key

6. 测试代码：
   - 不需要清理 test/ 下的英文断言、英文 fixture、英文测试名
   - 不要因为中文化日志去改测试文本，除非测试直接依赖内部日志且必须同步

示例：

可以改：

log_fail("OCR failed", e, url=url)

改成：

log_fail("OCR 失败", e, url=url)

可以改：

raise RuntimeError("PyMuPDF is not installed")

改成：

raise RuntimeError("未安装 PyMuPDF")

不要改：

return "[Tool Error] URL rejected by security policy: ..."

不要改：

"# OCR Supplement\n\nOCR failed: ..."

不要改：

TOOL_DESCRIPTION = "Fetch a web page..."

不要改：

parameters_schema["properties"]["force_ocr"]["description"]

二、精简冗余代码，重点审查超过 30 行的函数
============================================================

目标：
清理 AI 生成过程中产生的膨胀函数、重复逻辑、无意义 helper、复杂内联代码。

请重点排查所有超过 30 行的函数，包括但不限于：

1. WebFetchTool.execute
2. FetchCoordinator.fetch
3. StaticFetcher.fetch
4. LocalOcrProcessor._download_source
5. LocalOcrProcessor._request_worker
6. LocalOcrProcessor._stop_worker
7. paddle_ocr_worker.collect_texts
8. DocumentParser.parse
9. detect_doc_type
10. ContentProcessor._process_text / _process_html
11. container 注册函数
12. app_settings 配置类
13. 其他超过 30 行的函数

排查标准：

1. 如果函数长是因为自然业务流程清晰，不要强拆。
   例如：
   - 顺序式 pipeline
   - 明确的多分支降级链
   - 完整的安全校验流程
   - 完整的协议读写流程

2. 如果函数中存在多段重复逻辑，可以抽取。
   例如：
   - 多处重复构造 metadata
   - 多处重复日志格式
   - 多处重复 redirect 处理
   - 多处重复 ToolContentStore 缓存窗口逻辑
   - 多处重复 OCR 失败格式化

3. 如果函数中存在复杂内联代码，可以抽取为模块级 helper。
   适合抽取：
   - 不依赖 self 的纯逻辑
   - URL redirect 计算
   - 错误 message 格式化
   - metadata 构造
   - OCR markdown 合并
   - stdout/stderr 协议解析
   - 文件类型判断

4. 如果 helper 只被一个地方使用，并且逻辑很短，不要为了抽象而抽象。
   例如：
   - 简单的一行 bool 判断
   - 简单的一次性参数转换
   - 不复用的局部小逻辑

5. 如果 helper 不使用类内状态，不要放到类里。
   应放到模块级函数。

6. 如果逻辑使用类内状态，例如 self._min_content_length，可以放类内私有方法。

7. 不要把所有东西塞进 utils。
   只有跨模块通用的业务工具才进入 utils。
   当前倾向：
   - utils/text.py：文本规范化等通用文本处理
   - utils/url.py：URL 校验、安全校验、文档 URL 判断
   - utils/page.py：页面阻断/反爬/登录/JS 空壳检测

8. 不要把 FetchCoordinator 拆得过碎。
   降级链本身是核心业务流程，过度拆分会降低可读性。

9. 不要把 URL 安全逻辑复制到多个地方。
   统一使用 validate_public_http_url。

10. 不要手写内容截断。
    长内容统一走 ToolContentStore / cache_and_window / format_windowed_content / tool_content_read。

11. 不引入新的依赖来完成清理。

============================================================
三、统一代码风格
============================================================

请按照项目当前约定调整风格。

1. typing 风格

保持：
from typing import Any, Dict, List, Optional, Tuple, Literal

规则：
- Optional 仍然使用 Optional[T]
- 不要把 Optional[T] 改成 T | None
- 普通 Union 可以使用 A | B
- 已有 str | bytes 这类可以保留
- 不要大规模替换 typing 风格

2. 命名风格

模块级常量：
- 使用大写

模块级 helper：
- 如果是模块内部使用，不使用下划线前缀，但不在 __all__ 中导出。
- 如果是 public API，并在 __all__ 中导出，不加下划线

类内部属性和方法：
- 保持下划线规范

3. __all__ 风格

检查 __all__：
- 只导出真正的 public API
- 不要导出内部常量
- 不要二次导出从其他模块 import 进来的 helper
- 不要导出临时兼容函数，除非外部确实使用

4. pathlib 风格

文件路径统一使用 pathlib.Path。
不要新增 os.path 风格代码。
已有需要清理时，优先迁移到 Path。

5. 依赖注入风格

不要出现：

def __init__(self, dep: Optional[Dep] = None):
    self._dep = dep or create_dep()

原则：
- 如果对象由 container 装配，则构造函数参数必须显式传入。
- 不使用 Optional 依赖兜底。
- 不在业务类里偷偷 new 复杂依赖。
- container 保证装配成功。

6. 单例注册原则

不是所有单例都注册。
注册原则：
- 涉及装配、生命周期、配置、外部资源的单例应注册。
- 纯函数、无状态 helper 不注册。
- PaddleOCR engine 不注册进主服务 container，因为它只在 worker 子进程内加载。
- LocalOcrProcessor 可以注册，因为它涉及 worker 生命周期。

7. 日志风格

日志 stage 使用中文短语。
例如：
- “网页抓取”
- “静态抓取”
- “OCR 下载”
- “OCR worker”
- “URL 安全校验”
- “文档解析”
- “HTML 清洗”

日志字段名可以保持英文，例如：
url=...
backend=...
content_type=...
length=...
pid=...

8. 错误处理风格

不要宽容错误参数。
如果参数由 tool schema / settings / container 保证正确，不要写大量防御式 parse / clamp。

避免：
limit = min(max(1, limit), settings.TOOL_RESULT_MAX_CHARS)
bool(kwargs.get("force_ocr"))

应该：
- tool schema 保证类型
- settings 层保证配置正确
- 资源边界检查保留
- 安全边界检查保留

区别：
- URL 安全校验、文件大小、像素限制、超时，这是必要边界，必须保留。
- 对 settings 参数做 max(1, value) 这类静默修正，不建议保留。

9. async 风格

- 阻塞 DNS 解析放 asyncio.to_thread
- PDF 渲染放 asyncio.to_thread
- PaddleOCR 推理只在 worker 子进程内执行
- HTTP 下载使用 httpx.AsyncClient
- 不要在 event loop 内做重 CPU / 阻塞 IO

10. worker 协议风格

OCR worker 当前使用 JSON line 协议。
保持：
- stdout 只输出协议 JSON
- stderr 输出日志和 PaddleOCR 噪声
- 没有 request id，因此主进程 write/read 必须串行
- 不要缩小 _worker_lock 范围
- 不要缓存多个重模型
