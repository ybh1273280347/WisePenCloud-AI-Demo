对，这里我前面说“不要大改算法”太保守了。这个地方**应该改算法**，因为核心目标是 **offset 可靠**，不是“尽量少动”。

社区实践上，`RecursiveCharacterTextSplitter` 仍然适合作为通用文本 chunker：LangChain 文档把它描述为 generic text use cases 的推荐 splitter，它会按换行、空格等常见分隔符递归切分，直到 chunk 满足大小要求。([LangChain 文档][1])
但不能完全信任 `add_start_index=True` 产出的 `start_index`，因为社区里确实有多个相关问题：有人报告 `RecursiveCharacterTextSplitter(add_start_index=True)` 在某些文本上给出错误 start index；也有人报告 token-based splitter 继承 `TextSplitter` 后会出现 `start_index=-1` 或 offset 计算错误。([GitHub][2])

所以更有效的方案是：

> **继续用 `RecursiveCharacterTextSplitter` 负责切分内容，但不要用它的 `start_index`；我们自己按顺序把 chunk 映射回原文 offset。**

---

# 当前必须优化的点，为什么

## 1. 不再依赖 `doc.metadata["start_index"]`

之前代码：

```python
start = doc.metadata["start_index"]
```

这个不够稳。
即使 `add_start_index=True` 的设计目的就是把原文起始位置写进 metadata，LangChain 的 `TextSplitter` API 确实有这个参数，但社区 issue 说明它在一些 splitter / 文本组合下可能出错。([LangChain 参考文档][3])

应改为：

```python
pieces = splitter.split_text(text)
```

然后自己做顺序对齐：

```python
start = text.find(piece, search_from)
```

关键是 `search_from` 不是 `0`，而是上一个 chunk 的 `end_offset`。

这样可以避免重复文本错位。例如原文是：

```text
abc ... abc ... abc
```

如果每次都 `text.find(piece)`，会总是命中第一个 `abc`。
但用：

```python
text.find(piece, previous_end)
```

就会从上一个 chunk 后继续找，符合 `chunk_overlap=0` 的语义。

---

## 2. offset 生成必须建立自己的不变量

chunking 模块是整个窗口读取的地基。

必须保证：

```text
0 <= start_offset < end_offset <= len(text)
start_offset >= previous_end
index 连续
```

否则后续：

```python
find_chunk_by_offset
read_window
read_chunk_window
next_offset
returned_length
```

全部都会建立在错误 offset 上。

所以不应该“容忍并修正”非法 offset。
如果无法把 splitter 的 chunk 对齐回原文，应该直接抛错：

```python
raise ValueError("Unable to align chunk back to source text")
```

offset 错比失败更危险。

---

## 3. `strip_whitespace=False` 必须保留

这个配置是对的，不能改。

原因：如果 splitter 自己 strip 了 chunk，chunk 内容就不再是原文的精确子串，后续 `text.find(piece, previous_end)` 可能错位，`returned_length == len(window.text)` 的语义也会被破坏。

LangChain 的 `TextSplitter` 参数里确实有 `strip_whitespace`，默认行为可能会影响 chunk 边界；这里为了 offset 精确，必须显式保留 `False`。([LangChain 参考文档][3])

---

## 4. `find_chunk_by_offset` 继续保持简单，但要归一化 offset

这里可以保留线性扫描，因为 chunk 数通常不大，而且这个函数比二分更直观。

但要加：

```python
offset = max(0, offset)
```

让 helper 自己也具备基本防御。

---

# 需要确认一些东西再决定如何处理的点：需要确认什么，造成什么分歧

## 1. 未来是否要支持 `chunk_overlap > 0`

### 需要确认什么

现在配置是：

```python
chunk_overlap=0
```

但 RAG 社区里常见做法是给 chunk 加 overlap，用来减少语义被切断的概率；LangChain 的知识库示例就使用了 chunk overlap，并说明 overlap 有助于缓解上下文被切断的问题。([LangChain 文档][1])

### 造成什么分歧

如果长期保持：

```python
chunk_overlap=0
```

那么顺序对齐算法可以用：

```python
search_from = previous_end
```

如果未来支持 overlap，必须改成：

```python
search_from = max(0, previous_start + 1)
```

并且允许：

```python
start < previous_end
```

当前这个 store 是“窗口续读”基础设施，不是最终 RAG chunker，所以暂时保持 `chunk_overlap=0` 是合理的。

---

## 2. 对齐失败时是否 fallback 到 `add_start_index`

### 需要确认什么

如果：

```python
text.find(piece, previous_end) == -1
```

要不要尝试：

```python
doc.metadata["start_index"]
```

### 造成什么分歧

如果 fallback，工具更不容易失败，但可能把已知不可靠的 `start_index` 又引回来。

我的建议：**不要 fallback**。
既然我们改算法的目标是 offset 正确，就不要再依赖不可信来源。对齐失败直接抛错，配测试暴露问题。

# 如果只影响当前文件，直接输出完整代码

这次只影响当前 `chunking.py`，不影响其他文件或导入。建议改成下面这个版本。

```python
from typing import List, Optional

from langchain_text_splitters.character import RecursiveCharacterTextSplitter

from .models import ContentChunk


def create_content_chunks(text: str, chunk_size: int) -> List[ContentChunk]:
    if not text:
        return []

    chunk_size = max(1, chunk_size)

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=chunk_size,
        chunk_overlap=0,
        separators=["\n\n", "\n", " ", ""],
        length_function=len,
        add_start_index=False,
        strip_whitespace=False,
    )

    pieces = [piece for piece in splitter.split_text(text) if piece]

    chunks: List[ContentChunk] = []
    previous_end = 0

    for index, piece in enumerate(pieces):
        start = text.find(piece, previous_end)

        if start < 0:
            raise ValueError("Unable to align chunk back to source text")

        end = start + len(piece)

        if end > len(text):
            raise ValueError("Chunk end_offset exceeds text length")

        if end <= start:
            raise ValueError("Chunk end_offset must be greater than start_offset")

        if start < previous_end:
            raise ValueError("Chunk offsets must be non-overlapping and monotonic")

        chunks.append(
            ContentChunk(
                index=index,
                start_offset=start,
                end_offset=end,
            )
        )

        previous_end = end

    return chunks


def find_chunk_by_offset(chunks: List[ContentChunk], offset: int) -> Optional[ContentChunk]:
    offset = max(0, offset)

    for chunk in chunks:
        if chunk.end_offset > offset:
            return chunk

    return None
```

## 必须补的测试

```python
def test_create_content_chunks_handles_repeated_text_without_reusing_first_match():
    text = "abc\n\nabc\n\nabc"

    chunks = create_content_chunks(text, 3)

    assert [text[chunk.start_offset:chunk.end_offset] for chunk in chunks] == [
        "abc",
        "abc",
        "abc",
    ]
    assert [chunk.start_offset for chunk in chunks] == [0, 5, 10]


def test_create_content_chunks_offsets_are_monotonic():
    text = "alpha beta gamma delta"

    chunks = create_content_chunks(text, 6)

    previous_end = 0
    for chunk in chunks:
        assert chunk.start_offset >= previous_end
        assert chunk.end_offset > chunk.start_offset
        assert chunk.end_offset <= len(text)
        assert text[chunk.start_offset:chunk.end_offset]
        previous_end = chunk.end_offset


def test_find_chunk_by_offset_normalizes_negative_offset():
    chunks = [ContentChunk(index=0, start_offset=0, end_offset=5)]

    assert find_chunk_by_offset(chunks, -10) == chunks[0]
```

这版比“检查 `start_index` 是否存在”更有效，因为它直接规避了 LangChain `start_index` 的已知不稳定点，同时仍然保留 `RecursiveCharacterTextSplitter` 的社区通用切分策略。
